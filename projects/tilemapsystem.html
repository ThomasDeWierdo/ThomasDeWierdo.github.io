Tilemap System

Tilemap

 This system shows knowledge on optimization and shows how I can reduce the amount of repetitive tasks needed to implement new features.

Overview

 The tilemap system is in charge of rendering your world into visible blocks. Unity has a built-in tilemap system, but it would lag a lot when modifying tiles at runtime so I decided to create my own system. If you didn't look at the description of Perastra, it is the game I made this system for as it has a 2D pixelated grid-based sandbox world. The world is split up into 16x16 chunks of blocks, so all this system has to do is read the current data of a given chunk, then create a mesh that correctly renders all the individual blocks of that chunk. There is also an autotiling system that makes it so the same blocks can use slightly different textures to make it visually appear that blocks are connected and flow correctly with the surrounding blocks.

Techincal Deep-dive

 The main API for the tilemap system consists of 'create chunk', 'unload chunk', and 'get chunk' functions. A chunk takes up a 16x16 grid of blocks and is rendered using a single mesh. To create a chunk, it first makes a NativeChunkMesh instance, which is essentially a container for data needed in a chunk's mesh. It consists of 4 NativeList objects, so if I want to store multiple native chunks, I can set them side-by-side in the same data container. The reason for this design choice is because I need the chunk meshes to be able to be created inside and transferred out of Unity's jobs. A job is a system made by Unity that allows you to run code off the main thread, meaning it won't lag your game while running. To keep efficiency when using this system, it is recommended to create native objects, which are unmanaged structs that also can't have containers in containers, which is why I had the NativeChunkMesh have lists that store per-chunk mesh data contiguously rather than using a list of native chunk meshes.
 So, in the actual code to generate the mesh to write to the native chunk mesh, it iterates over each block in the given chunk, and depending on what tile type that block has, it will write different data for a quad to put in the chunk. For example, if the block is a multiblock (meaning it takes up more than one tile of space), on its root block, it will add a quad around the bounds of that multiblock, and it won't add any quad for the non-root blocks. If nothing is there, it won't add any quad. There are also a bunch of other tile types I've made that require different data, but I'll talk about that more later with the autotiling system.
 With all the quads created, if it was called by a job off the main thread, it first has to finish the job and send the native chunk mesh to the main thread, otherwise it can be converted directly to a mesh and displayed. I also have the unload chunk functions that just unload a targeted chunk if it's loaded, and the refresh chunk functions refresh the targeted chunk, rerunning the process described earlier.
 There is also a quad editor system here that allows you to get a pointer to a specific quad on a chunk mesh. You add a quad editor to a ChunkMesh instance at a selected position, then whenever you refresh the chunk, it will make sure to set the exact index of the quad you want into the quad editors. So far I've used it to make a custom effect for vines to make them sway in the wind. To do this, I used my block behavior system, then for the root vine, it gets references to the quads of every vine in the group of vines, then edits the quad vertex positions using the API of the quad editor to get the desired visual effect.
 Now onto the autotiling system, which runs entirely on the GPU for optimization. The CPU first writes a bunch of data depending on the tile type of each quad through the color channel. This data contains the tile type first, then any other data that tile type needs. Then, inside the shader, it automatically performs the autotiling functions before rendering. For example, if that tile uses the RuleTile16 type, it will have access to if it connects to the blocks around it, then calculate which of the 16 textures in the given spritesheet is correct.
 Another tile type that I've made is the Subtiles4 type, which allows the spritesheet to only be the size of a single tile while still being able to connect properly to every combination of surrounding tiles. It leads to repeated texturing, but it's great for testing new blocks without much work towards a texture. I made this when I realized that every texture to form a spritesheet for a block that can connect to adjacent or diagonal blocks can be represented by orienting just 4 subtiles, which are quarters of a single tile. There is a side subtile, open subtile, corner subtile, and inner corner subtile.
 There are a bunch of different types for different purposes and they allow me to create new blocks without having to create a massive spritesheet for every orientation of a block. My choice for most organic blocks is the MarchingSquares8 type, which uses a modified version of a method I found online to tile organic textures together, allowing me to create 8 tiles for all the connection combinations - still a huge jump from a previous 47 tiles. Then if you want some more variation in each displayed texture, I also give the option to make variants for a spritesheet that the autotiling system swaps between every block.

Final Notes

 The actual tilemap chunk system here I don't think is crazy or super unique, but I'm very happy with my autotiling system as it saves so much time having these different spritesheet format options.
